# Application Surfaces Decisions

## Ambiguity Resolutions

- "Dashboard stage migration" could mean backend schema only or the full configuration surface. Resolved: **Dashboard Stage Configuration Surface Cutover** is part of Slice 1 and includes API payload fields, helpers, UI labels, fixtures, and tests.
- "Workflow Template Execution Result" could mean the final API/RunStore artifact shape or the governed facts returned by template execution. Resolved: it is the typed execution facts only; Delivery and Observability still own trace files, Governance Receipt rendering, RunStore persistence, and Dashboard projection.
- "Dashboard Models" could mean a provider model catalog, reusable connection assets, or Agent-only model fields. Resolved: use **Models Workspace** for administering live **Shared Model Connections**; Agent roles and Knowledge Sources may select a shared connection or use custom model configuration.
- "No Agents in chat" could mean falling back to examples, auto-importing a template, or showing a setup state. Resolved: chat shows an empty state and points to the **Agent Configuration Workspace**; only explicit import, validation, and publication make an Agent chat-accessible.
- "Configuration permissions" could mean full enterprise RBAC or no permission model at all. Resolved: first-stage configuration may be single-user, but the **Agent Configuration Permission Model** and **Configuration Operation Audit** fields are part of the domain model.
- "YAML editor" could mean a second source of truth, an export pane, or a contract-level editor. Resolved: use **Contract View** as an advanced view over the same Draft Agent state, validated before save or publication.
- "Management console" could mean internal run observability, Dashboard-hosted Agent configuration, or a full platform administration product. Resolved: V1 keeps an **Internal Governance Dashboard** for observability; Agent configuration belongs in an **Agent Configuration Workspace** hosted by the **Dashboard Shell** with separate configuration APIs; full **Agent Control Platform Console** work is future scope.
- "Agent builder" could mean a blank free-form graph editor or a guided Contract-first setup. Resolved: new Agents start in an **Agent Creation Wizard** and continue in the **Agent Configuration Workspace**.
- "Dashboard navigation" could mean a separate builder app, a settings page, or Agent-centered operations. Resolved: use an **Agent-Centric Dashboard Shell** with global observability and Agent detail views for monitoring and configuration.
- "Handoff monitoring" could mean a dashboard projection or a full ticket workflow. Resolved: V1 provides **Internal Handoff Monitor** only; assignment, SLA, notification, and ticket status workflows are future scope.
- "Shared chat frontend" could mean one unrestricted UI or a shared shell with separate audience projections. Resolved: use **Unified Chat Frontend** for a shared design and interaction shell, with customer mode limited to **Customer-Safe Response Projection**.
- "Dashboard sidebar" could mean a flat list, role-based sections, or monitoring/configuration separation. Resolved: the **Dashboard Shell** sidebar uses two **Sidebar Navigation Section** groups: MONITORING for observability and CONFIGURATION for design-time views.
- "Agent configuration sub-features" could mean grouped concerns, workflow stages, or contract artifacts. Resolved: the **Agent Configuration Workspace** uses **Agent Configuration Module** tabs (General, Workflow, Knowledge, Tools, Policy, Model, Memory, Response) organized by contract artifact.
- "Agent detail navigation" could mean horizontal tabs, vertical tabs, or a sectioned page. Resolved: the **Agent Configuration Workspace** uses vertical tabs in the main content area with CONFIGURE and LIFECYCLE sections.
- "Configuration editing" could mean forms only, visual builders, code only, or a hybrid. Resolved: each **Agent Configuration Module** uses a **Configuration Module Editor** with forms for common settings and YAML toggle for advanced editing.
- "Validation interface" could mean a simple test runner, test suite, or validation dashboard. Resolved: the Validate & Test **Agent Lifecycle Tab** uses a **Validation Workspace** grouped by Draft Readiness, Run Validation, Latest Validation Result, Validation History, and gated validation capture sections.
- "`Knowledge Hub`" could mean a new runtime, a retrieval engine, or the product-facing configuration surface for reusable knowledge. Resolved: **Knowledge Hub** names the Shared Asset Library capabilities for Knowledge Sources and Agent Knowledge Bindings, while retrieval still enters the Control Envelope through governed Knowledge Provider Adapters and evidence admission.
- "Knowledge Source workspace route" could mean adding `/knowledge-sources`, keeping the existing `/knowledge`, or embedding all file management under one Agent. Resolved: evolve the existing `/knowledge` page into the global **Knowledge Source Workspace** and do not add `/knowledge-sources`.
- "Knowledge Source detail route" could mean a modal, an Agent-embedded document manager, or a reusable-asset detail page. Resolved: use **Knowledge Source Detail Workspace** at `/knowledge/:sourceId`; Hybrid Sources use Overview, Documents, Reviews, Versions & Publish, Operations, Provider & Health, and Audit tabs, while Agent pages link to it without embedding full file management.
- "Knowledge Source list" could mean a thin link list, raw Agent YAML excerpts, or an operational reusable-asset inventory. Resolved: **Knowledge Source Workspace List Projection** shows identity, metadata, provider, lifecycle, availability, published version, local document counts or remote target, Agent reference count, and warning indicators, with filters for name, tag, provider, lifecycle, and warning state.
- "Create a Knowledge Source" could mean one frontend-hardcoded provider form, a deployment-mode branch in Dashboard, or a server-capability-driven wizard. Resolved: **Knowledge Source Creation Wizard** renders the **Knowledge Source Provider Capability Projection** from the active Proof Agent service; production exposes Hybrid Index Knowledge Source creation, development may expose Local Index and remote-adapter paths, and no path publishes implicitly.
- "Operate a 500-document local source" could mean a raw upload list, one-file-at-a-time management, or a paginated document workspace. Resolved: **Knowledge Source Documents Tab** provides batch upload, state filters, pagination, revision visibility, per-document and bulk actions, routing metadata edits, and a persistent candidate-snapshot publication summary.
- "Configure a remote Knowledge Source" could mean raw JSON only, a fixed adapter-specific form, or layered descriptor-driven configuration. Resolved: **Remote Knowledge Source Provider Tab** uses common fields by default, bounded advanced mappings when supported, typed forms for registered remote adapters, and mapping editors for `http_json`; connection testing and retrieval preview never publish implicitly.
- "Configure local index" could mean mixing files and model settings, exposing every setting at once, or using a layered provider form. Resolved: **Local Index Provider Tab** keeps file management in Documents, exposes common model and routing defaults first, folds timeout, retry, concurrency, and routing-model override into advanced settings, offers a non-ingesting model-configuration test, and marks artifact-affecting ingestion changes as **Local Index Reingestion Required**.
- "Complete Hybrid Knowledge configuration in Dashboard" could mean stopping after upload, stopping after Source publication, or activating a production Agent Version. Resolved: Dashboard V1 completes the Hybrid Index Knowledge Source lifecycle through explicit Source publication and shows the resulting Agent binding upgrade opportunity; candidate-bound Phase F evidence, Agent publication, and Active Agent Version transition remain in the controlled production release workflow.
- "Expose Knowledge Source configuration APIs in development and production" could mean two mode-specific public routers, one router with production fallback, or one stable contract backed by injected implementations. Resolved: Dashboard consumes one **Knowledge Source API Contract** and one **Knowledge Source Provider Capability Projection**; deployment composition may inject different implementations, but production fails closed and never selects a development implementation or local-storage fallback.
- "Retain a Development Knowledge Hub implementation" could mean permanently maintaining a file-backed management plane, merging its behavior into the production path, or removing it after migration. Resolved: remove the deployable Development Knowledge Hub implementation after the stable API cutover; local Dashboard integration uses the production-grade Knowledge application service against disposable dependencies, while standalone package-local Markdown execution and test-only fakes remain available outside Knowledge Hub.
- "Configure Hybrid private model services in Dashboard" could mean editing deployment endpoints and credentials per Source or presenting deployment-owned capability state. Resolved: Knowledge Source configuration never edits private parser, scheduler, embedding, or reranker endpoints, credentials, Egress Policy, or model digests; Dashboard presents their trace-safe capability, pinned revision, and health projections, while deployment configuration and Secret Provider remain authoritative.
- "Unify the Knowledge application service" could mean one large service object, one domain module with focused application services, or one process containing API, workers, and execution. Resolved: keep one Knowledge application boundary and public API contract while separating Configuration, Ingestion, Publication, and Operations application services; Knowledge Worker and Run Executor remain independently composed process roles that consume the same authorities and ports.
- "Describe Knowledge Source capabilities" could mean one deployment-wide flag set, action probing through failed commands, or layered projections. Resolved: **Knowledge Source Provider Capability Projection** declares deployment-level provider, intake, feature, and sanitized readiness facts, while **Knowledge Source Action Capability Projection** declares Source-specific allowed and blocked actions after Source state, permission, dependency, and conflicting-work checks; every command still revalidates authoritatively.
- "Upload a Dashboard document batch" could mean one Base64 JSON batch request, direct browser upload to artifact storage, or bounded client orchestration. Resolved: Dashboard submits one multipart document per Proof Agent API request, limits concurrent submissions, and presents independent per-file outcomes; Proof Agent retains admission, system-generated storage identity, authorization, and audit authority.
- "Keep Dashboard informed about asynchronous Knowledge work" could mean a permanently open request, mandatory SSE, or bounded polling of durable state. Resolved: V1 uses server-guided polling of Knowledge Source Operation Projection while work is active, pauses background polling when the page is hidden, applies bounded backoff, and reloads authoritative Source and action projections on terminal completion; future SSE may only provide a refresh hint over that same durable state.
- "Retry a Dashboard mutation after an uncertain network result" could mean issue a fresh command, infer success from the refreshed Source, or replay a stable command identity. Resolved: Dashboard preserves one `Idempotency-Key` per intended retryable mutation until terminal state and reuses it for transport retries; it generates a new key only for a new operator intent and surfaces `idempotency_key_mismatch` as a client defect or stale persisted action rather than silently retrying.
- "Import Hybrid metadata workbooks from Dashboard" could mean Base64 JSON, direct artifact upload, or reuse of the file-command workflow. Resolved: Dashboard sends one `.xlsx` as multipart with its exact document and revision binding, Source concurrency token, and Idempotency Key, then follows the returned durable operation and opens the resulting review set only after atomic completion.
- "Publish a Hybrid Source from Dashboard" could mean hold the browser request through index projection, hide a long publish operation behind a spinner, or separate durable preparation from atomic authority change. Resolved: Dashboard follows an asynchronous publication-validation operation to a Prepared Hybrid Knowledge Publication, presents its exact summary for confirmation, and then submits a short idempotent publication CAS; Source publication success is shown only after the authoritative Source projection confirms the new published version.
- "Report a Knowledge Source API failure" could mean return arbitrary `detail`, expose downstream errors, or publish one stable safe problem contract. Resolved: every failure is a Knowledge Source API Problem using `application/problem+json`; Dashboard branches and localizes only on stable `code`, honors explicit retry guidance, and never receives raw dependency exceptions, endpoints, credentials, storage paths, or authorization-sensitive resource facts.
- "Name and version the unified Knowledge Source API" could mean introduce a parallel `/v1` route family, retain mode-specific aliases, or cut over the existing configuration namespace. Resolved: `/api/config/knowledge-sources` is the sole resource root, `/api/config/knowledge-source-capabilities` projects deployment capabilities, Source detail embeds Source action capabilities, and `knowledge-source-api.v1` permits additive evolution; breaking change requires an explicit future version rather than silent drift or permanent legacy aliases.
- "Page large Knowledge Source collections" could mean load every item, expose offsets, or use one bounded opaque cursor contract. Resolved: documents, revisions, operations, jobs, reviews, publications, and audit return Knowledge Source Cursor Page with keyset cursors, default limit 50 and maximum 100, server-whitelisted stable ordering, and authoritative aggregate summaries independent of page contents.
- "Offer Retry and Cancel in Dashboard" could mean infer actions from a displayed status, always enable both buttons, or consume Source action capabilities. Resolved: Dashboard renders per-job Retry or Cancel only when the Source action projection permits it, preserves an Idempotency Key for the operator command, shows attempt history separately from revision history, and never treats cancellation of replacement work as removal of the previous READY candidate.
- "Organize Hybrid Source administration" could mean keep Review and Operations as Overview panels, reuse the Local Index tab set unchanged, or expose lifecycle-focused workspaces. Resolved: Hybrid Source detail uses seven tabs: Overview, Documents, Reviews, Versions & Publish, Operations, Provider & Health, and Audit; capability projections control actions, and tab visibility never grants authority.
- "Authorize Hybrid business review" could mean reuse ordinary Source edit, treat Source publication as review authority, or declare a distinct permission. Resolved: `knowledge_source.review` gates correct, approve, and reject; import remains `knowledge_source.edit`, Source publication remains `knowledge_source.publish`, and Audit requires `audit.view`. Capability projections reflect these grants, but every command authorizes again server-side.
- "Preserve legacy Development Knowledge Hub data" could mean retain runtime dual-read, migrate automatically on startup, discard everything, or offer an explicit one-shot tool. Resolved: provide dry-run and manifest-producing Development Knowledge Hub Migration for supported shared Sources, allow disposable local environments to skip it, and delete the file-backed router, store, and fallback after migration acceptance rather than exposing compatibility behavior in Dashboard.
- "Rollback a Knowledge Source" could mean mutating history, rewinding a shared production pointer, or preparing a reviewed replacement. Resolved: **Knowledge Source Versions Tab** creates a **Knowledge Source Rollback Draft** from a historical version, requires fresh validation and publication for a new version, and never automatically changes Published Agent Versions or Draft Agent bindings.
- "Agent-specific monitoring" could mean a separate tab, split view, or lifecycle integration. Resolved: the Monitor **Agent Lifecycle Tab** appears under LIFECYCLE alongside Validate & Test, Versions, and Contract View.
- "Workflow editing" could mean a linear list, visual diagram, accordion, or tabbed editor. Resolved: the Workflow **Agent Configuration Module** uses an expandable accordion showing all nodes with inline configuration fields.
- "Agent creation" could mean inline form, modal wizard, or template selection. Resolved: the **Agent Creation Wizard** starts with template selection (Enterprise QA, Customer Service, Blank) before collecting agent details.
- "Remote validation" could mean a production deployment, direct exposure of three local dev servers, or one review URL over local services. Resolved: use a **Remote Verification Session** with a **Remote Verification Gateway** and optional public quick tunnel; it is a development verification path, not production hosting.

## Relationship And Reference Notes

- Application surfaces configure or observe governed facts through APIs; they must not bypass core Harness workflow, policy, evidence, approval, or trace boundaries.

- Presentation vocabulary belongs here when it describes UI slicing or labels rather than runtime semantics.

- A **Remote Verification Gateway** routes `/api` to the backend API, `/operator` and `/customer` to **Unified Chat Frontend**, and all other browser paths to **Internal Governance Dashboard**.
- A **Remote Verification Session** may stop existing Python, Node, Vite, npm, uvicorn, Proof Agent, or cloudflared processes only when they are tied to configured verification ports or the matching quick tunnel target.
- A **Remote Verification Session** defaults to public quick tunnel exposure and fails before cleanup or startup when `cloudflared` is unavailable; `--local-only` keeps the same single local gateway without external exposure.
- Extending Sensitive Validation Capture Retention through `retain_for_audit` requires an explicit authorized validation/test-run request and must show the artifact expiry or audit-retention status in Dashboard.
- **Dashboard Stage Configuration Surface Cutover** changes Agent Configuration API request and response fields to `stages`, renames Dashboard helpers to stage terminology, updates UI labels from legacy node-labeled panels to stage-centered surfaces, and migrates Dashboard tests and fixtures in the same Slice 1 cutover.
- An **Assisted QA Chat Frontend** submits questions through the **Run Execution API**.
- A **Unified Chat Frontend** may share design, navigation rhythm, and message-composition flow across **Assisted QA Chat Frontend** and **Customer Service Chat Frontend** modes.
- A **Unified Chat Frontend** must not expose audit links, **Governance Detail Projection**, approval state, raw run identifiers, or receipt links in customer mode.
- A **Unified Chat Frontend** does not merge **Run Execution API** and **Customer Run API** response contracts; audience-specific projections remain separate.
- **Assisted QA Chat Frontend** mode may expose conversation management and internal audit affordances that **Customer Service Chat Frontend** mode must hide.
- The **Assisted QA Chat Frontend** resolves waiting approval through **Approval Checkpoint Resume**, not by starting a new follow-up run with an inline approval decision.
- The **Assisted QA Chat Frontend** uses **Controlled Conversation Context** for automatic multi-turn context injection.
- The **Dashboard Model Configuration** module presents **Context Window & Budget** controls next to model role settings because operators understand context window size through model usage. These controls still write top-level **Agent Context Configuration** under `context.budget_profile`; they must not be stored under `model`, `react.planner`, `review.subagent`, or shared model connection parameters.
- The **Agent Configuration Workspace** exposes **Agent Memory Configuration** per Agent and does not treat memory as a reusable cross-Agent asset in the first implementation stage.
- The **Dashboard Memory Configuration Module** remains the Agent Configuration Module for retained memory capability settings and Memory Recall Admission narrowing. It does not own Working Context budget, convergence ladder, or dynamic calibration controls.
- The **Dashboard Memory Configuration Module** writes only canonical Agent Contract locations: retained memory capability settings under `capabilities.memory` and run-start context policy under `context`. It does not preserve or read legacy top-level `memory` fields.
- The first **Dashboard Memory Configuration Module** makes **Case Memory** and consent-gated **Persistent User Memory** editable memory scopes, while **Shared Memory** remains disabled until cross-user governance is defined.
- The first **Dashboard Memory Configuration Module** uses a fixed section order for cache-stable review and editing: Provider & Enablement, Case Memory, User Memory, Shared Memory Disabled State, Memory Recall Admission, Stage Visibility, and Lifecycle & Audit.
- The first **Dashboard Memory Configuration Module** keeps unsupported memory sections visible as disabled or read-only controls with explicit blocking reasons. Structurally valid Draft Agent configuration may be saved while gated, but Validate & Test and publication must block when the provider is missing, a persistent provider has no enabled memory scope, or **Shared Memory** is enabled.
- The first **Dashboard Memory Configuration Module** treats Memory Recall Admission as a narrowing policy over enabled memory scopes. A recall policy may disable Case or User recall, but it cannot enable recall for a memory scope that is not enabled under `capabilities.memory`; **Shared Memory** recall remains unavailable.
- The first **Dashboard Model Configuration** module displays runtime dynamic defaults for the optional context budget override without persisting them until an operator overrides a budget control. Budget override writes only `context.budget_profile`; Dashboard does not synthesize convergence ladder or dynamic calibration defaults from the Model module.
- The first **Dashboard Memory Configuration Module** writes Memory Recall Admission only to `context.source_policies.memory_recall`; it must not synthesize `context.budget_profile`, convergence ladder, or dynamic calibration defaults.
- The first **Dashboard Memory Configuration Module** limits Lifecycle & Audit to retention, expiry, deletion policy, audit requirements, and blocking-state explanation. Memory record browsing, record-level deletion or editing, and recall audit-detail inspection belong to later Memory Operations and Audit slices after provider-backed record APIs are stable.
- **Dashboard Memory Configuration Module** work should land in this order: canonical Agent Contract path cutover, fixed visible section rendering, gated readiness behavior, default-versus-override persistence, and regression coverage for YAML paths, editor interactions, module integration, and domain docs.
- V1 keeps the existing dashboard role as an **Internal Governance Dashboard** and does not deliver an **Agent Control Platform Console**.
- Agent configuration planning extends the **Dashboard Shell** with an **Agent Configuration Workspace** while preserving separate configuration, execution, and observability API boundaries.
- The Dashboard Shell should become **Agent-Centric**: global observability remains available, and each Agent detail view combines monitor, configure, validate/test, versions, and Contract View.
- The existing Dashboard `/knowledge` route becomes the global **Knowledge Source Workspace** for shared Knowledge Source administration; the product may label the navigation item "Knowledge" or "Knowledge Sources", but it does not add a parallel `/knowledge-sources` route.
- The **Knowledge Source Workspace** links each Source to **Knowledge Source Detail Workspace** at `/knowledge/:sourceId`. Hybrid administration uses Overview, Documents, Reviews, Versions & Publish, Operations, Provider & Health, and Audit; Agent Knowledge modules remain focused on binding selection, bounded overrides, resolved versions, and upgrade actions.
- The `/knowledge` **Knowledge Source Workspace List Projection** shows Source identity, description, tags, provider type, ACTIVE or ARCHIVED lifecycle, local index or remote verification availability, current published snapshot or configuration version, local READY and total document counts or remote target index or namespace, referencing Agent count, and warnings for unpublished changes, failed ingestion, or stale remote verification. Operators may filter by name, tag, provider, lifecycle, and warning state.
- **Knowledge Source Creation Wizard** starts from `/knowledge` and renders only providers and lifecycle actions declared by **Knowledge Source Provider Capability Projection**. Production declares `hybrid_index`; development may declare `local_index`, `http_json`, or other explicitly supported development adapters. Dashboard does not infer deployment mode, maintain an independent provider allowlist, or publish a Source implicitly.
- For a `local_index` source, **Knowledge Source Documents Tab** supports batch PDF and Markdown upload; filtering by name, tag, and state; pagination; and per-row document name, current READY revision, pending revision, state, update time, and current-published-snapshot membership. Single-document actions include replace, failed-revision retry, routing-metadata edit, archive, and revision history. Bulk actions include failed-revision retry, archive, and tag edit.
- **Knowledge Source Documents Tab** persistently shows a Candidate Knowledge Source Snapshot summary with included READY count, processing count, failed count, archived count, and explicit Publish Source action.
- **Remote Knowledge Source Provider Tab** uses a default form for adapter, endpoint, environment-variable credential references, index or namespace, timeout, and default `top_k`, plus an advanced section for supported protocol, request mapping, response JSON Pointer mapping, and Structured Remote Source Reference mapping. Typed remote adapters prefer descriptor-driven forms, while `http_json` exposes bounded mapping editors.
- **Remote Knowledge Source Connection Test** validates connectivity, authentication, target existence, and normalization shape. **Remote Knowledge Source Retrieval Preview** runs a bounded query and displays normalized candidates, citations, Provider-Native Relevance Scores, and Remote Knowledge Revision Observations. Neither action publishes a Source; a saved Draft still requires successful verification and explicit Knowledge Source Publication.
- **Local Index Provider Tab** uses a default form for ingestion model provider, model, environment-variable credential references, inherited routing model, and Knowledge Document Selection Budget defaulting to 8, plus an advanced section for explicit routing-model override, timeout, retry count, and worker concurrency. File and routing-metadata management remains in Knowledge Source Documents Tab.
- **Local Index Model Configuration Test** validates model settings and referenced credential availability without triggering a full rebuild. A change to ingestion configuration that could affect index artifacts sets **Local Index Reingestion Required**; published snapshots remain usable, but the replacement candidate snapshot cannot be published until required document revisions are reingested successfully.
- Dashboard shows the count of revisions requiring rebuild and exposes `Reingest required documents`. Current published snapshots continue serving while rebuilding, and a replacement candidate snapshot cannot publish until all required revisions are READY.
- **Knowledge Source Versions Tab** lists published snapshots or configuration versions with publication time, actor, `change_note`, validation result, referencing Agent count, and version diff. Rolling back creates a **Knowledge Source Rollback Draft** from the selected historical version rather than mutating history or moving a production pointer.
- Hybrid Dashboard management ends after explicit **Knowledge Source Publication** and presentation of **Knowledge Binding Upgrade Available**. It does not collect Phase F evidence, invoke production Agent publication, move the Active Agent Version pointer, or present Source publication as production Agent activation.
- The **Knowledge Source API Contract** keeps route, command, projection, error, authorization, and concurrency semantics stable across deployment compositions. Capability differences are explicit data; Dashboard must not infer them from mode labels, missing routes, static provider lists, or failed command probes.
- Removal of the Development Knowledge Hub implementation does not remove the deterministic package-local Markdown example or test-only fakes. It removes the separately deployed file-backed Knowledge Source management lifecycle and any local-storage fallback from Dashboard integration.
- Knowledge Source configuration owns Source intake limits and Source lifecycle facts, not private model-service deployment. Missing or incompatible private-service capabilities block the affected Source action and remain visible as sanitized readiness facts instead of becoming editable endpoint fields.
- Configuration owns Source commands and projections; Ingestion owns admitted-document work; Publication owns candidate validation and atomic Source visibility; Operations owns trace-safe health and backlog projections. These responsibilities share contracts and authorities but do not collapse API, Knowledge Worker, and Run Executor into one process or one stateful service object.
- Dashboard first loads **Knowledge Source Provider Capability Projection** to build provider creation paths, then consumes **Knowledge Source Action Capability Projection** from Source detail to render current actions and blocker explanations. Neither projection exposes private endpoints, Secret Handles, raw dependency errors, or content-bearing data.
- Dashboard batch upload is a presentation workflow over independent single-document commands. A failed item does not roll back accepted uploads, and Dashboard refreshes the authoritative Source projection after the bounded submission set settles.
- Dashboard exposes replacement as an explicit action on one stable Knowledge Document and sends the new file to its revisions collection. Matching filename never implies replacement; while the new revision processes or fails, Dashboard continues to show the prior READY revision as the candidate and separately shows the pending or failed revision.
- A successful asynchronous Knowledge Source command returns `202 Accepted` with `operation_id`, `source_revision`, and `poll_after_ms`. Dashboard may honor `Retry-After` when present, stops polling terminal operations, and can recover progress after reload because operation state is not held in browser memory or an API process callback.
- Knowledge Source Command Idempotency is checked before `expected_revision` on a replay, so a successfully committed command can return its original outcome after response loss even though the Source revision has advanced. First execution still performs the full permission, state, dependency, request-fingerprint, and optimistic-concurrency checks.
- Knowledge Source API Problem maps request size, media type, and semantic validation to `413`, `415`, and `422`; separates revision, stale-validation, lifecycle-state, and idempotency conflicts under stable `409` codes; and marks bounded `429` or `503` responses retryable with `Retry-After` when applicable. Structured `blockers` explain permitted business actions, while forbidden requests fail without leaking hidden Source or dependency facts.
- Dashboard routes remain `/knowledge` and `/knowledge/:sourceId`; API route versioning is independent of browser navigation. After the Dashboard cutover, Base64 batch routes, mode-specific DTOs and routers, and development fallbacks are removed rather than retained through dual writes, aliases, or silent forwarding.
- Knowledge Source cursors bind the resource, normalized filter, and sort specification. Changing that query restarts pagination; `cursor_invalid` or `cursor_expired` restarts from the first page. Dashboard treats aggregate `summary` as authoritative and never derives publication readiness or backlog totals from loaded rows.
- **Agent Configuration MVP** prioritizes the vertical import-to-publication-to-monitoring loop before full Tool Source management, advanced Policy condition building, unbounded multi-source retrieval, full RBAC, deep visual diffs, or memory lifecycle UI.
- **Agent Configuration MVP** uses a **Workflow Stage Panel** for Workflow Template Stage Configuration before adding any visual workflow canvas.
- New Agent setup enters through an **Agent Creation Wizard** and then lands in the module-based **Agent Configuration Workspace** for ongoing edits.
- The first **Agent Configuration Workspace** may run as a single-user local experience, but it should still preserve **Agent Configuration Permission Model** roles and **Configuration Operation Audit** metadata for future RBAC.
- V1 includes an **Internal Handoff Monitor** for handoff visibility and run-detail drilldown, but not assignment, SLA, notification, or ticket workflow.

## Presentation Vocabulary Notes

- Page, Page Size, Offset, and Last Page remain presentation vocabulary for existing offset-based Dashboard lists; Knowledge Source collections instead expose Knowledge Source Cursor Page and do not translate cursor state into a backend offset.
- Approval queue status vocabulary is a view filter. Pending and Expired queue views describe unresolved approvals by `expires_at`; they do not replace the PendingApproval lifecycle.
- Chinese Dashboard navigation keeps `Runs` and `Agents` in English while translating `policies`, `knowledge`, `models`, and `tools`, following the established Chinese PRD terminology.
