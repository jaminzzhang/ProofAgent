# Use one Knowledge Source API contract

[FRAME | HIGH] Dashboard uses one stable Knowledge Source API contract with an explicit provider-and-action capability projection. Deployment composition may temporarily supply different development and production implementations during migration, but their public route semantics cannot diverge, and production must fail closed rather than select a development implementation or local-storage fallback. The target state removes the deployable Development Knowledge Hub implementation: local Dashboard integration uses the production-grade Knowledge application service against disposable dependencies, while package-local Markdown execution and test-only fakes remain outside Knowledge Hub.

[FRAME | HIGH] Private Knowledge model-service endpoints, credentials, Egress Policy, and model digests remain deployment-owned. The API projects sanitized capability and readiness facts to Dashboard but does not turn Knowledge Source configuration into a deployment-secret or model-serving control plane.

[FRAME | HIGH] The capability contract has two layers: a deployment-level provider projection for creation paths, intake envelopes, feature families, and sanitized readiness; and a Source-level action projection for currently allowed or blocked lifecycle commands. Dashboard uses both for presentation, while every command repeats permission, state, dependency, concurrency, and freshness checks against authoritative state.

[FRAME | HIGH] Mutable Knowledge Source projections carry a monotonic `revision`, and Source-state commands compare an explicit `expected_revision`, returning a stable conflict instead of accepting last-write-wins updates. `source_draft_version_id` remains a separate publication-freshness identity that changes only when the publication candidate changes; review resources and publication validation retain their stronger resource-specific identities and compare-and-swap rules.

[FRAME | HIGH] Retryable mutations require an `Idempotency-Key` scoped to operator, Source, and command type. The API retains its canonical request fingerprint and original outcome for at least 24 hours. Exact replay returns that original outcome before evaluating `expected_revision`; reuse with different request content returns `409 idempotency_key_mismatch`. A new key is a new command even when the artifact layer can reuse identical immutable bytes.

[FRAME | HIGH] Every failure uses `application/problem+json` with stable `type`, `status`, and `code`, safe `title` and `detail`, a trace-safe `trace_id`, explicit `retryable`, and only bounded optional `current_revision`, field-error, or action-blocker facts. Dashboard localizes and branches on `code`; raw downstream exceptions and sensitive endpoints, credentials, Secret Handles, storage paths, and authorization facts do not enter the response. Size, media, and semantic validation map to `413`, `415`, and `422`; distinct `409` codes cover optimistic concurrency, stale validation, lifecycle conflicts, and idempotency mismatch; applicable `429` and `503` responses include bounded retry guidance.

[FRAME | HIGH] `/api/config/knowledge-sources` remains the sole public resource root, with deployment/provider capabilities at `/api/config/knowledge-source-capabilities` and Source-specific actions embedded in Source detail. The capability projection declares `schema_version: "knowledge-source-api.v1"`; V1 evolves only through compatible optional additions, while a future breaking contract requires an explicit new version. Dashboard browser routes remain `/knowledge` and `/knowledge/:sourceId`. Once cut over, mode-specific routers and DTOs, Base64 batch endpoints, and development fallbacks are deleted rather than kept as aliases or dual-write paths.

[FRAME | HIGH] Documents, revisions, operations, jobs, reviews, publications, and audit collections use one opaque keyset-cursor envelope with default limit 50 and maximum 100. A cursor binds resource, normalized filters, and a server-whitelisted deterministic sort with immutable identity tie-breaker; it is never interpreted as an offset by Dashboard. Repository queries apply the limit before materialization. Server-owned aggregate summaries remain separate from page contents, and invalid or expired cursors produce stable problems that cause Dashboard to restart from the first page.

[FRAME | HIGH] Legacy file-backed Source state is not a second implementation of this contract. An explicit one-shot migration tool may import supported shared Source state before cutover, but application startup, Dashboard, and production composition never dual-read, auto-migrate, or fall back to the legacy store. The old router and store are deleted after migration acceptance.
