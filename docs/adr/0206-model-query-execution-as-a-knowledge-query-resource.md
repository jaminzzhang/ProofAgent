# Model query execution as a precisely named Knowledge Query resource

[FRAME | HIGH] Knowledge Source Service exposes one versioned HTTP JSON and OpenAPI query contract centered on the domain resource Knowledge Query rather than generic `query-operation`, `operation`, `task`, or `job` terminology. The public routes are `POST /v1/knowledge-queries`, `GET /v1/knowledge-queries/{knowledge_query_id}`, and `POST /v1/knowledge-queries/{knowledge_query_id}:cancel`. Public contracts consistently use `knowledge_query_id`; job, queue, lease, and worker identities remain internal implementation details.

[FRAME | HIGH] Create Knowledge Query requires a mandatory `Idempotency-Key`, exact `knowledge_base_release_id`, `question`, `strategy` (`single_pass` or `agentic`), typed `query_constraints`, optional `access_narrowing_context`, `execution_budget`, and absolute `deadline_at`. Idempotency is scoped to the authenticated Agent client and binds one canonical request fingerprint to one Knowledge Query. An exact replay returns the same resource and immutable terminal result; key reuse with another fingerprint fails with a stable conflict. `Prefer: wait=N` changes only how long the create request waits: completion may return the terminal resource immediately, while unfinished work returns `202 Accepted`, `Location`, and the same resource for polling. Cancellation is explicit, and a cancelled or expired query cannot later commit a successful result.

[FRAME | HIGH] Knowledge Query State is `queued`, `running`, `succeeded`, `failed`, `cancelled`, or `expired`; `expired` means execution missed its deadline before success. Successful-result retention is represented separately by `result_availability` and `result_expires_at`, so content cleanup never rewrites execution history. One successful Knowledge Query Result contains `evidence_groups[]`, `query_plan_summary`, `execution_summary`, and `retrieval_lineage`. Each Evidence Group is discriminated by `group_type: relevance_ranked | structured`, declares its own ordering semantics, and contains `candidate_evidence[]`. Relevance-specific values use explicit names such as `lane_contributions`, `fused_rank`, and `reranked_rank`; Structured results use `structured_order`. The contract deliberately omits generic `score`, `confidence`, `accepted`, `truth`, and `answer` fields so retrieval relevance cannot be mistaken for Evidence Admission or factual authority. Problems use RFC 9457 `application/problem+json` plus a stable service `code`.

[FRAME | HIGH] V1 treats polling of the durable Knowledge Query as authoritative. Future SSE may deliver advisory state-change notifications but cannot become a second state or result authority. We accept a durable query resource and mandatory idempotency so fast single-pass retrieval and longer Agentic retrieval share one precise contract, retries do not duplicate model cost or lineage, and Proof Agent can safely resume after receiving `202 Accepted`.
